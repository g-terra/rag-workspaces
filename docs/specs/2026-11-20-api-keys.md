# API keys, admin-created, workspace-bound, hashed at rest (auth 2/3)

## Summary

Admins create API keys (`rw_...`) bound to workspaces with a role (`reader` or `editor`). The secret is
shown once; only its SHA-256 hash is stored. A request with a key is authenticated like a Keycloak
token and `GET /v1/me` describes the key. Workspace binding is stored here and enforced in #13.

## Why

Decision 9 (API keys created by admins only, bound to workspaces, role reader or editor). Agents and
scripts need credentials that don't depend on a browser login.

## Design

1. Migration `0001_api_keys.sql`: `api_keys` (name, display prefix, `secret_hash` unique, role, created
   by, expires at, last used at, revoked at) and `api_key_workspaces` (cascades on key or workspace
   delete); enum `workspace_role` (`reader`, `editor`).
2. `apps/api/src/auth/api-keys.ts`: create `rw_` + 32 random bytes in base64url (46 characters); authenticate by
   `sha256(secret)` index lookup; 401 for unknown, revoked or expired; update `last_used_at` at most
   once a minute per key, never failing the request.
3. `apps/api/src/routes/api-keys.ts`: five admin-only routes.
4. `auth/plugin.ts`: `requireAdmin` and `currentUser` guards.
5. `packages/shared`: `WorkspaceSlug`, `page()` list wrapper, API key shapes.
6. `@rag/db/testing` `createTestDatabase()`: one fresh migrated database per test file.

## Decisions and trade-offs

| Decision | Alternatives considered | Why this one |
| --- | --- | --- |
| SHA-256 of a 256-bit random secret | bcrypt/argon2 | Slow hashes protect weak passwords; a random secret can't be brute-forced, and a fast hash allows index lookup |
| Revoke keeps the row (`revokedAt`) | Delete the row | The usage log can still show the key's name; `DELETE` is idempotent |
| Role can't change after creation (PATCH `role` → 400) | Allow it | An existing secret never silently gains editor rights |
| Lists return everything, `nextCursor: null` | Pagination now | A personal install has few keys |

## Interfaces and contracts

- **HTTP API** (admin only; others 403):
  - `GET /v1/api-keys`, `GET /v1/api-keys/{id}`.
  - `POST /v1/api-keys` → 201 with `secret` (once).
  - `PATCH /v1/api-keys/{id}` (name, workspaces, expiry; unknown workspace 422; revoked key 409).
  - `DELETE /v1/api-keys/{id}` → revoke.
  - `GET /v1/me` for a key → `{ kind: 'key', id, name, role, workspaces }`.
- **Configuration**: None.
- **Data**: tables `api_keys`, `api_key_workspaces`; enum `workspace_role`. Display prefix is the first
  7 characters (`rw_7Hk2`).
- **Langflow**: None.
- **Events and logs**: None.

## Operations

Hard to undo: the `rw_` format and the hashing scheme; changing them invalidates every issued key. A lost
secret can't be recovered: revoke and create a new key.

## Testing

`apps/api/src/routes/api-keys.test.ts` against Postgres: create shows the secret once and the stored row
never contains it; auth with valid, revoked and expired keys; non-admins and keys get 403 on every
route; PATCH rules (role 400, unknown workspace 422 keeps bindings, revoked 409); `lastUsedAt` updates.
Skipped locally without `TEST_DATABASE_URL`.

## Out of scope and follow-ups

Enforcing workspace scope (#13), per-key request counts (usage log, #22), pagination, rate limiting.
