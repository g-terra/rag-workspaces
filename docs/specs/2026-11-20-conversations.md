# Conversations with history through a new rw-chat flow

## Summary

Adds conversations: a person or key starts one in a workspace and sends messages; each reply is grounded
and cited like an answer, and can stream. History is stored in our database and sent to a new stateless
`rw-chat` flow on each message. The answer logic moves into a shared `Generator` used by answers and chat.

## Why

The "chat" part of the brief and decision 11 (conversation history lives in our database only; the flow
is stateless).

## Design

1. `apps/api/src/services/conversations.ts`, `send`: load the last `CHAT_HISTORY_TURNS` turns (each
   earlier message cut to 2,000 characters, failed replies left out), build the search query from the
   previous user message plus the new one, call the generator, store both messages.
2. `apps/api/src/services/generate.ts`, `Generator`: the answer steps from #19/#20 (retrieve, resolve,
   ungrounded shortcut, run, parse, store failures); with `history` it runs `rw-chat` instead of
   `rw-answer`.
3. `apps/api/src/routes/streaming.ts`: shared streaming response (first-token open, always ends).
4. `flows/chat.json`: generated by `poc/client/build-flows.ts`, which now writes `rw-` names to `flows/`
   (the other four flows regenerate byte for byte).
5. Migration `0005_conversations.sql`: `conversations` and `messages`, one enum.

## Decisions and trade-offs

| Decision | Alternatives considered | Why this one |
| --- | --- | --- |
| Stateless flow, history in Postgres | Langflow's message store | One place for history, one delete, tests don't depend on Langflow state |
| Search with previous + new user message | Ask the model to rewrite the question | No extra model call; upgrade if it proves weak |
| `ChatInput` carries the search query; `Question` and `History` are text inputs | Separate search input | Langflow drops outputs not downstream of the chat input (lost citations) |
| Conversations private to their starter and admins | Shared in the workspace | Same rule as answers |
| Refactor and feature in one PR | Split the `Generator` refactor | The refactor exists only so chat can share it |

## Interfaces and contracts

- **HTTP API** (reader):
  - `POST /v1/workspaces/{slug}/conversations` `{ title? }`;
  - `GET .../conversations` (own, most recently active first, paginated);
  - `GET .../conversations/{id}` (with messages);
  - `DELETE .../conversations/{id}`;
  - `POST .../conversations/{id}/messages` `{ content }` → the cited reply, or SSE with
    `Accept: text/event-stream` (same events as answers).

  Others' conversations → 404.
- **Configuration**: `CHAT_HISTORY_TURNS` (10).
- **Data**: tables `conversations`, `messages`.
- **Langflow**: new flow `rw-chat`: `ChatInput` = search query; text inputs `Question`, `History`;
  `Search`, `Embeddings`, `Prompt`, `LLM` tweaks as in `rw-answer`. `/ready` requires `rw-chat`.
- **Events and logs**: None new.

## Operations

Restart Langflow once to import `rw-chat` (`docker compose restart langflow`); `/ready` fails until then.
The migration adds one enum and two tables; nothing existing changes.

## Testing

`apps/api/src/routes/conversations.test.ts`: create, list own only, history building and truncation,
follow-up search query, failed replies excluded from history, streaming, another user's GET/DELETE 404,
workspace scoping. Answer tests pass unchanged after the refactor. Live: a follow-up came back grounded
with a citation; a streamed reply sent 16 token events through nginx.

## Out of scope and follow-ups

Question rewriting with the model; conversation titles generated from the first message.
