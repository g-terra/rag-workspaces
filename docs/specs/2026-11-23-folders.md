# Folders, upload into a folder, and moving, renaming or retagging documents

## Summary

A workspace can now have folders, for example a course code. What changes:

- Editors create, rename and delete folders.
- Editors upload straight into a folder.
- Editors move, rename or retag a document with `PATCH`.
- The library can be filtered by folder, or by the top level.

Passages carry the folder's id in Chroma, so a move or a folder delete updates them in place, with no
reindex. Limiting search, answers and chat to one folder is the next PR.

## Why

docs/decisions.md ("Folders inside a workspace: optional, used as a filter"), docs/architecture.md
("Workspaces") and docs/work-breakdown.md (M1, M4 items 4 and 5) plan folders. The admin UI's library and
upload screens wait for them. Document `PATCH` was also still planned.

## Design

1. **Data** (`packages/db/src/schema.ts`, migration `0007_folders.sql`):
   - A new `folders` table (`fld_` id, `workspace_id`, `name`, timestamps), unique on
     `(workspace_id, lower(name))`.
   - `documents.folder_id`, nullable, `ON DELETE SET NULL`, indexed.
   - Folders are flat.
2. **Folder routes** (`apps/api/src/routes/folders.ts`):
   - `GET` lists the folders by name, with `documentCount`. Readers may list.
   - `POST` and `PATCH` create and rename; a name already used in the workspace is `409`. Editors only.
   - `DELETE` refuses with `409` while a document in the folder is processing. Otherwise it sets each
     document's passages to the top level in Chroma first, then deletes the row, which lets the foreign key
     clear `folder_id`, then emits a `document` event for each moved document. If Chroma fails part way,
     nothing is deleted and a retry finishes the job.
3. **Documents** (`apps/api/src/routes/documents.ts`):
   - Upload takes `?folderId=` (a folder of this workspace, else `404`).
   - The list takes `folderId=<id>` or `folderId=none`.
   - The new `PATCH` takes any of `folderId` (null for the top level), `title` and `tags`. Its conditional
     `UPDATE` refuses while the document is `processing` or `transcribing` (`409`).
   - A move then calls `ChromaService.setDocumentFolder`. If that fails, the row is put back and the answer
     is `503`.
4. **Chroma** (`apps/api/src/services/chroma.ts`): `setDocumentFolder` gets the document's vector ids and
   `update`s their metadata with `{ folder: <id> | null }`. Chroma 1.5 merges metadata on update, and `null`
   removes the key; I checked this against the stack's Chroma.
5. **Ingestion** (`apps/api/src/services/ingest.ts`): the `Loader` tweak now sends
   `folder: <folder id or ''>`. It is taken from the row the run claimed, so a move that lands while the
   document is queued is honoured. The loader component and the search filter already existed in the
   flows.

## Decisions and trade-offs

| Decision | Alternatives considered | Why this one |
| -------- | ----------------------- | ------------ |
| The folder id goes in Chroma metadata | Keep folders out of Chroma and filter by a list of document ids (the work-breakdown fallback) | The search component already filters on `folder`, and Chroma updates metadata in place, so a move is two small requests. A list of ids would grow with the folder and still needs a flow change |
| Store the id, not the name | The name | A rename is then a database change only |
| Flat folders | Nested | Nothing asks for nesting. A course code per folder is the use case |
| Folder delete moves documents to the top level | Delete the documents too, or refuse unless empty | Matches what docs/api-schema.md promised. Deleting material is the document `DELETE`'s job |
| Upload's folder as a query parameter | A multipart field | Fields and files arrive interleaved in a multipart stream. A query parameter is checked before any file is staged |
| Moving is refused while a document is ingested | Let the run pick it up | The run writes vectors with the folder it started with |
| Chroma first on delete, database first on a move with rollback | Always the same order | A move must take the claim (the conditional update) before touching Chroma. A folder delete has nothing to claim and can simply be retried |

## Interfaces and contracts

- **HTTP API**:
  - `GET` and `POST /v1/workspaces/{slug}/folders`. `GET` is for readers and returns `page(Folder)`;
    `POST` is for editors and answers `201 Folder`, or `409` for a name in use.
  - `PATCH` (rename, `200 Folder`) and `DELETE` (`204`, `409` busy, `503` Chroma down) on
    `/v1/workspaces/{slug}/folders/{folderId}`.
  - `Folder` is `{ id, workspace, name, documentCount, createdAt, updatedAt }`. `FolderInput` is
    `{ name }` (1 to 100 characters).
  - `Document` gains `folderId: string | null`.
  - `POST .../documents?folderId=` and `GET .../documents?folderId=<id>|none`.
  - `PATCH .../documents/{id}` with `UpdateDocument { title?, folderId?: string | null, tags? }` (strict)
    answers `200 Document`, `404` for an unknown folder, `409` while it is processing, or `503` when Chroma
    is down.
- **Configuration**: None.
- **Data**: migration `0007_folders.sql`: the `folders` table, `documents.folder_id`, and two indexes.
  Passages ingested from now on carry `folder` in Chroma when they are in a folder.
- **Langflow**: the `rw-ingest` `Loader` tweak now always sets `folder`. No flow JSON changed.
- **Events and logs**: a move, rename or retag, and a folder delete, emit `document` events for the
  documents they changed.

## Operations

The migration runs on API start. Existing documents stay at the top level, and their passages have no
`folder` key, which means the top level. Nothing needs reindexing.

## Testing

- `apps/api/src/routes/folders.test.ts` (8 tests):
  - create, list with counts, rename (no Chroma calls), and case-insensitive name clashes;
  - readers can't change folders;
  - uploading into a folder, and the `folderId` and `none` filters;
  - a folder from another workspace is refused on upload and on move;
  - a move updates every vector's metadata, a move to the top level sends `null`, and a retag touches
    nothing;
  - `409` while processing, and a move undone when Chroma is down;
  - a folder delete waits for Chroma, then moves its documents out, and is refused while one is busy.
- `apps/api/src/services/ingest.test.ts`: the loader gets the document's folder.
- `scripts/smoke/check.ts`, on the real stack with real Chroma: moving a document puts the folder id on
  every passage, and deleting the folder removes it.

- Folder-level permissions (folders isolate nothing, by design).
