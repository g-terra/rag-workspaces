# Database package with Drizzle, migrations on start and the workspaces table

## Summary

Adds `packages/db`: the Drizzle schema (starting with `workspaces`), committed SQL migrations, a client
with `ping` and `close`, and prefixed ULID ids. The API applies pending migrations before it listens and
refuses to start if one fails. `/ready` now checks Postgres too. CI runs the database tests against a
throwaway Postgres.

## Why

Decision 16 (the database schema is its own package) and decision 15 (Postgres holds app data and the
queue). M1 needs the `workspaces` table first; every later feature PR adds its own tables.

## Design

- `packages/db/src/schema.ts`: Drizzle tables; `workspaces` with id, slug (unique), name, description,
  `settings` jsonb, timestamps.
- `packages/db/drizzle/0000_init.sql` + `drizzle/meta/`: generated by `pnpm --filter @rag/db
  db:generate`; applied by `runMigrations(url)` or `db:migrate`.
- `packages/db/src/client.ts`: `createDb(url)` → `{ db, ping, close }` using postgres.js with
  `casing: 'snake_case'`.
- `packages/db/src/ids.ts`: `newId(prefix)` → `ws_01J...`-style ULIDs, no extra dependency.
- `apps/api/src/main.ts` startup order: config → migrations → db → Langflow service → app (with a
  Postgres readiness check) → listen → Langflow key.

## Decisions and trade-offs

| Decision | Alternatives considered | Why this one |
| --- | --- | --- |
| Drizzle with generated, committed SQL migrations | Prisma; hand-written SQL | Readable SQL in review; typed queries; small runtime |
| camelCase in TS, snake_case in Postgres via `casing` | Same names both sides | Idiomatic on both sides; set once |
| Text ULIDs with a type prefix, made by the API | UUIDs, sequences | Sort by time (cursor pagination), prefix tells what an id is in logs |
| `settings` as one typed `jsonb` | One column per setting | Optional overrides read together; new ones need no migration; shape checked by zod in the API |
| postgres.js 3.4.9 | 4.x | Drizzle 0.45 is tested against 3.x |
| API exits if Postgres is unreachable at start | Start and report not ready | The API can do nothing without its database; compose restarts it |

## Interfaces and contracts

- **HTTP API**: `/ready` also fails when Postgres doesn't answer.
- **Configuration**: `DATABASE_URL` (postgres://rag@postgres:5432/rag) for the API; `TEST_DATABASE_URL` for DB tests (listed in
  `turbo.json` so Turborepo passes it through).
- **Data**: table `workspaces`; migration bookkeeping in `drizzle.__drizzle_migrations`.
- **Langflow**: None.
- **Events and logs**: migration log lines on start.

## Operations

- **Never edit a migration that has run anywhere; add a new one.** Drizzle tracks applied files.
- Migrations take a lock and are idempotent, so restarts re-apply nothing.
- Hard to undo: the casing rule and the id format.

## Testing

`packages/db/src/db.test.ts` (migrations apply and re-apply, defaults, unique slug) and `ids.test.ts`
(ULID reference value). CI runs them against a Postgres service; locally they skip without
`TEST_DATABASE_URL`. By hand: `docker compose logs api | grep migrations`,
`docker compose exec postgres psql -U rag -d rag -c '\d workspaces'`.
