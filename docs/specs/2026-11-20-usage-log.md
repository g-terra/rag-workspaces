# Usage log of every API request for analytics

## Summary

Every `/v1` request becomes a row in `api_requests` when its response ends: route pattern, status,
latency, workspace, caller and, for answers and chat replies, the question, model, grounding, tokens and
cited documents. Question text is cleared after 90 days. This is the data half of usage analytics; the
reports come next.

## Why

The brief's "analytics on API usage" and the plan's usage-log design ("usage rows are kept" after
deletes).

## Design

1. `apps/api/src/usage/log.ts`: a Fastify plugin that, in `onRequest`, listens to the raw response's
   `finish` (logged with its status) and `close` (a hang-up before finish is logged as 499), once.
   `UsageLog` writes rows without awaiting, with `flush()` and `trimQuestions(days)`.
2. `apps/api/src/usage/details.ts`: what answers and chat replies add (`req.usage`).
3. Answer, message and passage routes set `req.usage`; searches record their query only.
4. `apps/api/src/main.ts`: trims question text on start and every 6 hours; flushes on shutdown.
5. Migration `0006_usage_log.sql`: `api_requests` with indexes on time, workspace + time,
   caller + time.

## Decisions and trade-offs

| Decision | Alternatives considered | Why this one |
| --- | --- | --- |
| Write after the response, fire and forget | Write inside the request | Logging never slows or fails a request; a failed write loses one row |
| Raw `finish`/`close` events | Fastify `onResponse` | Streamed responses bypass `onResponse` |
| Store route patterns; unmatched → `(no route)` | Raw paths | Paths can carry ids or anything a caller typed |
| No foreign keys | FKs to workspaces and keys | Rows outlive deleted workspaces and revoked keys |
| Copy question text, clear after 90 days | Join to answers | Analytics survive deletes; personal data doesn't stay forever |

## Interfaces and contracts

- **HTTP API**: none new; `/health`, `/ready`, `/docs` aren't logged.
- **Configuration**: `USAGE_QUESTION_RETENTION_DAYS` (90).
- **Data**: table `api_requests` (id, created_at, request_id, method, route, status_code, latency_ms,
  workspace_slug, workspace_id, caller_kind, caller_id, question, answer_id, message_id, model, grounded,
  prompt/completion tokens, time_to_first_token_ms, cited_document_ids).
- **Langflow**: None.
- **Events and logs**: warning when a usage row fails to write.

## Operations

A stream that ended with an `error` event is logged as 200 (the answer row says failed). The table grows
one row per request; no row deletion yet.

## Testing

`apps/api/src/usage/log.test.ts`: rows for answers and chat replies with details, route patterns,
`(no route)`, hang-up as 499, retention clears only old question text, flush on shutdown. Live: an answer
through the admin proxy produced one row with route, 201, latency, workspace, caller, question, model
and `grounded`.

## Out of scope and follow-ups

The reports (#26). Row retention and pre-aggregation for big installs.
