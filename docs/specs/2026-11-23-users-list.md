# List the people in Keycloak with GET /v1/users

## Summary

Admins can now list the people in the `rag-workspaces` realm with `GET /v1/users`: id, username, email,
name, whether they are an admin and whether the account is enabled, with search and paging. The admin UI
uses it to grant someone workspace access before their first sign-in. The API reads Keycloak's admin API
as a new confidential client, `api-directory`, whose service account can only view users.
`pnpm env:init` now also tops up an existing `.env` with secrets added since it was written.

## Why

Decision 12 (`docs/decisions.md`): accounts are created in Keycloak's console, and our admin UI lists
people read-only and grants them workspace access. `PUT /v1/workspaces/{slug}/members/{userId}` already
takes a Keycloak user id, but nothing told an admin which ids exist. The admin UI's members screen
(M4) needs this route; it was listed as planned in `docs/api-schema.md` and `docs/architecture.md`.

## Design

1. `docker/keycloak/realm.json` adds the client `api-directory`: confidential, service account only (no
   browser login, no password grant), secret `${RW_API_DIRECTORY_SECRET}`. Its service account user holds
   `realm-management: view-users` and nothing else. The client's default scopes are `basic`, `roles` and
   `kc-admin-api`: Keycloak 26.8 rejects admin API tokens whose audience is not the admin API ("Expected
   audience not available in the token"), and `kc-admin-api` is the built-in scope that adds it.
2. `docker-compose.yml` passes `KEYCLOAK_DIRECTORY_SECRET` from `.env` to Keycloak (as the realm
   placeholder) and to the API. `.env.example` marks it `<generated>`.
3. `apps/api/src/services/people.ts`, `KeycloakDirectory`: gets a client-credentials token from the
   internal Keycloak URL and reuses it until 30 seconds before it expires. `list()` calls
   `GET /admin/realms/rag-workspaces/users` with `first`, `max` (one more than asked, to know whether a
   next page exists) and Keycloak's own `search`, then asks each listed person's composite realm roles
   (eight at a time) to set `isAdmin`. `GET /roles/admin/users` would be one call, but needs `view-realm`.
4. `apps/api/src/routes/users.ts`: `GET /v1/users`, `requireAdmin`, query `UserQuery`, response
   `page(User)`, both in `packages/shared/src/users.ts`. Registered in `apps/api/src/app.ts` under a new
   `users` OpenAPI tag. The cursor is the offset into Keycloak's list.
5. `scripts/env-init.ts`: an existing `.env` keeps every value; any `<generated>` key it lacks is
   appended with a fresh secret. Before, it refused to touch an existing `.env`.

## Decisions and trade-offs

| Decision | Alternatives considered | Why this one |
| -------- | ----------------------- | ------------ |
| A separate `api-directory` client | Turn the bearer-only `api` client into a confidential one with a service account | `api` is the audience our API accepts. A service account on that client could mint tokens our API would treat as a signed-in person. `api-directory` tokens carry the admin API audience, which our API rejects. |
| `view-users` only, one role lookup per person | Add `view-realm` and list `admin` holders in one call | Least privilege: `view-realm` also exposes realm settings. Listing is a page of at most 100 people in a personal tool, and lookups run eight at a time. |
| The API's master admin login is not used | Sign in as `KEYCLOAK_ADMIN` | That account can change anything in Keycloak; the API should never hold it. |
| `503` when the secret is missing or refused | Fail at start-up | The rest of the API works without the people list, and the error says what to do. |
| `env:init` tops up an existing `.env` | Ask people to copy the new line by hand; wait for the `pnpm setup` wizard | Compose refuses to start without `KEYCLOAK_DIRECTORY_SECRET`, so every existing install needs it now. The wizard (plan item 14) takes this over later. |

## Interfaces and contracts

- **HTTP API**: `GET /v1/users?search=&limit=&cursor=` (admins only) returns
  `{ data: [{ id, username, email, name, isAdmin, enabled }], nextCursor }`. `limit` is 1 to 100, default
  50. `email` and `name` are `null` when Keycloak has none. `400` for a malformed cursor, `401` without
  credentials, `403` for a non-admin or any API key, `503` when Keycloak is unreachable, the secret is
  missing or Keycloak refuses it.
- **Configuration**: `KEYCLOAK_DIRECTORY_SECRET` (required by compose, generated by `pnpm env:init`);
  `KEYCLOAK_DIRECTORY_CLIENT_ID` (API only, default `api-directory`).
- **Data**: realm `rag-workspaces` gains the client `api-directory` and its service account user. No
  database change.
- **Langflow**: None.
- **Events and logs**: None.

## Operations

- After pulling, run `pnpm env:init`; it adds `KEYCLOAK_DIRECTORY_SECRET` to `.env`. Compose refuses to
  start until it is there.
- Keycloak imports `realm.json` only into an empty database. An existing realm does not get the new
  client: `GET /v1/users` then answers `503` saying the client was not accepted. Either reset the stack
  (`docker compose down -v`, which deletes its data) or create the client by hand in the Keycloak console
  as `realm.json` describes it, with the secret from `.env`. The README's new "Updating an existing
  install" section says the same.
- Rotating the secret: change it in the Keycloak console and in `.env`, then restart the API.

## Testing

- `apps/api/src/services/people.test.ts`: against a fake Keycloak. Maps people (names joined, missing
  fields `null`, admin from realm roles), pages with the one-extra trick, passes the search through,
  reuses the token, and answers `503` for a missing secret, a refused secret and an unreachable Keycloak.
- `apps/api/src/routes/users.test.ts`: admins only (`403` for a non-admin and for API keys, `401` for
  nobody), query defaults and pass-through, a bad cursor is `400`, the directory's `503` comes back as a
  problem.
- `scripts/smoke/check.ts` gains a step: `GET /v1/users` lists the seeded admin with `isAdmin: true`,
  through the real Keycloak and the real `api-directory` client. The smoke test passed with it.
- Checked by hand against Keycloak 26.8.2 with this realm: the service account can list users and read
  role mappings, cannot create a user (`403`), and its token is refused without the `kc-admin-api` scope.

## Out of scope and follow-ups

- Creating or editing people stays in Keycloak's console (decision 12).
- The admin UI's members screen, which calls this route, is built in the admin UI thread.
